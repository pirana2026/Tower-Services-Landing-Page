Drone Phenology Monitoring

End to end system of drone imagery collection, processing and phenology monitoring.

Use the service ↗

About this service

Drone Phenology Monitoring is a web application that turns a time series of drone orthomosaics into a phenology map at individual tree-crown resolution. Each run is isolated: you create it, upload the orthomosaics, pick a model and parameters, and the pipeline runs end to end. Earlier runs stay available for comparison, so you can try different settings on the same site without losing anything.

Crown detection uses Detectree2 (Mask R-CNN). A graph-based tracker links the same crown across orthomosaic dates, and the phenology step uses those chains to decide whether a crown is deciduous and when its leaves fell and returned. When the run finishes, an interactive viewer opens the result as a clickable map: pick any crown and read its full phenology record on top of the orthomosaic.

How to use it

1
Sign in and create a run: Sign in with Google. From the dashboard, create a new run. Each run keeps its own uploads, parameters, logs and outputs, so you can compare runs later. The service does not re-run an existing run; changing parameters means a new run.
2
Upload orthomosaics: Add GeoTIFFs (.tif / .tiff) of the same site at different dates. Each file must carry a coordinate reference system in its metadata. If an orthomosaic is missing a CRS, you are prompted to select one before the pipeline starts.
3
Pick a model and parameters: Choose a Detectree2 weight (for example 250312_flexi for mixed sites, or canopy-specific weights). Set the tracking parameters, or keep the defaults.
4
Run the pipeline: Start the run. The four pipeline steps execute one after another and the browser streams their logs live. If you close the tab, the run keeps going on the server; come back later and the logs and finished outputs are still there.
5
Review and export: Open the interactive viewer to inspect crowns and phenology overlays on top of the orthomosaic. Download the phenology vector (GeoPackage / GeoJSON), the per-crown CSV, the crown polygons, the pipeline log and the STAC Item from the per-run file browser.

Methodology

How Drone Phenology Monitoring Works?

Detectree2 (Mask R-CNN) · Graph-based tracker · Cloud-Optimised GeoTIFF · Leaflet.js · FastAPI · Airflow + STACD

1UploadOrthomosaics of one site, many dates
2DetectDetectree2 outlines every crown
3TrackSame crown linked across dates
4ClassifyGCC curve to deciduous or evergreen
5ExploreClickable map with a date slider

System architecture

  • The pipeline worker computes, FileBrowser stores, and the dashboard only reads. A run's results, once written, do not depend on the worker to be served.
  • Upload path: orthomosaics (GeoTIFFs with an embedded CRS) go from the browser to the FastAPI service, which validates the CRS, writes the files and records acquisition dates in the database.
  • Pipeline worker: runs the four-step pipeline inside Docker and writes outputs to /app/data/<run_id>/outputs. GPU inference is used for detection.
  • Scheduling: when the upload completes, FastAPI triggers the drone_phenology_monitoring DAG in Airflow with the run_id and any overridden parameters. The DAG runs the Phenology_Export root algorithm, which calls the pipeline's /api/export-phenology endpoint.
  • Storage: every run has its own folder with uploads, intermediate outputs and the final viewer. FileBrowser gives read-only share links for each folder.
  • Web dashboard: a FastAPI JSON API serves run metadata, triggers runs and streams per-step status. A Leaflet.js front end draws the viewer, polls run status every five seconds, and shows signed-in users only their own runs.
  • Standalone viewer: each run also produces a self-contained viewer.html with relative paths, so it opens in any browser without the backend.

The pipeline: four steps in sequence

The moment you click Upload & start pipeline, the four steps run one after another. Each step writes to a run-specific folder and the next step picks the files up automatically.

StepWhat happens
1 · Crown Detection
01_crown_detection.py		In: orthomosaic GeoTIFFs. Out: per-date crown GeoPackages. A fine-tuned Detectree2 (Mask R-CNN) model outlines every visible crown. Overlapping detections are merged so each crown is counted once, with a confidence score per polygon.
2 · Crown Tracking
02_crown_tracking.py		In: per-date crown GeoPackages. Out: consensus crowns GeoPackage. Anchor crowns align the dates by phase-correlation, then crowns are matched by IoU and centroid distance so each tree keeps one ID. Only crowns seen in enough dates (base_threshold) survive, which filters out false detections and transient objects.
3 · Phenology Analysis
03_phenology_analysis.py
10_phenophase_classifier.py
12_apply_phenophase_to_geojson.py		In: consensus crowns. Out: final annotated GeoJSON. A Green Chromatic Coordinate (GCC) time series is extracted per crown and reduced to a Deciduousness Score (DS), which classifies each crown as deciduous or evergreen. The label is written into the GeoJSON that the viewer loads and that QGIS users download.
4 · Interactive Viewer
04a_cog_tiling.py
04b_interactive_viz.py		In: orthomosaics + final GeoJSON. Out: self-contained Leaflet map. Orthomosaics are tiled into Cloud-Optimised GeoTIFFs so the viewer loads only the tiles it needs. The map has clickable crowns, a date slider across acquisition dates, and a switch between the orthomosaic and a false-colour vegetation view.

Crown detector: Detectree2

  • Open-source tree-crown detector using Mask R-CNN instance segmentation.
  • Published weights are used as they are. Nothing is retrained per site.
  • Three weight options can be picked when you start a run:
Model variantWhen to use
urban_canopyMixed urban / peri-urban canopy; well-separated crowns. Default.
250312_flexiGeneral-purpose; a good first fallback if urban_canopy underfits.
tropical_denseDense tropical closed-canopy forests with heavy crown overlap.

Tracking a crown across dates

  • Align: high-confidence anchor crowns are used to line up every date with a tiled phase-correlation (align_method = pcc_tiled).
  • Match: crowns from different dates are linked by IoU and centroid distance, so one tree keeps one ID throughout the series.
  • Filter: a crown must appear in enough dates to be kept. This removes false detections and transient objects such as vehicles or shadows.
ParameterDefaultWhat it does
base_threshold45How many dates a crown must appear in to be kept. Raise it to drop more transient detections, lower it to retain more.
align_threshold65Confidence floor for the anchor crowns used in alignment.
align_methodpcc_tiledPhase-correlation on tiles.

Phenology and the Deciduousness Score

  • A Green Chromatic Coordinate (GCC) time series is extracted for every tracked crown.
  • Four phenological signals are combined into one Deciduousness Score (DS) using four weights: w_veg_amp, w_depth, w_gcc_amp and w_tex.
  • The classifier uses the DS to label each crown deciduous or evergreen, and to tell when leaves fell and returned.
  • Default weights are tuned for mixed temperate / subtropical forests. The Parameter Guide covers tuning for other biomes.

Outputs

  • Interactive viewer (viewer.html): date slider, clickable crowns, tooltips with tracked ID and phenophase, and a base-map switch between the orthomosaic and a false-colour vegetation view.
  • Final annotated GeoJSON (final_annotated_crowns.geojson): all tracked crowns with their phenophase label. The main deliverable for QGIS.
  • Phenology metrics GeoJSON (phenology_metrics.geojson): raw metrics before classification, for your own analysis of the fitted curves.
  • COG tiles (cogs/): one Cloud-Optimised GeoTIFF per date, reusable in any COG-aware GIS tool.
  • STAC item: the per-crown vector is registered by STACD (DPM_Phenology_Vector) so it can be found in the shared catalog.
  • Public listing: toggle a run Public and its viewer appears on the DPM landing page, open to anyone without signing in.
  • Portable run folder: the viewer and tiles use relative paths, so the whole folder can be moved and still opens.

Limitations and what they imply

LimitationWhat it means
Detection needs visible canopyUnderstorey trees hidden under taller crowns are not detected. Only nadir drone imagery is supported; oblique captures are not.
Phenology needs temporal coverageAt least 5 dates across the active season are needed; 8 to 12 dates, 2 to 3 weeks apart, are ideal. Missing leaf-out or leaf-off lowers phenophase accuracy.
Alignment assumes overlapA survey that flew a very different path on one date may fail alignment for that date.
Classification depends on DS weightsDefaults suit mixed temperate / subtropical forests. Other sites may need the Parameter Guide's tuning procedure.
Weights are not retrainedDetection quality depends on how close your site is to the training data, so pick the closest model variant.
Illumination must be consistentLow-sun shadows add spectral noise. Fly within ±2 hours of solar noon on every date.
Boundary must be consistentChanging the survey polygon between dates changes which crowns are detected and tracked. Reuse the exact saved flight plan every date.
